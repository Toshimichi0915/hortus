# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

hortus is a terminal coding agent (TypeScript, pnpm workspace): `@hortus/core` (providers, tool loop, sessions, plugins) and `@hortus/cli` (Ink TUI), plus reference plugins (kept outside this repo).

## Commands

```sh
pnpm build          # tsc -b packages/cli (project references build core too)
pnpm dev            # build, then run node packages/cli/dist/index.js
pnpm test           # build, then node --test over packages/*/dist/**/*.test.js
pnpm lint           # biome lint
pnpm format         # biome format --write
```

Tests run from compiled `dist/`, so build first. Single test file: `pnpm build && node --test packages/core/dist/session.test.js` (add `--test-name-pattern "<name>"` to pick one test). Tests use `node:test` + `node:assert/strict`, colocated as `*.test.ts(x)`.

Whole-run tests use `@hortus/core/testing` (`testing.ts`): `scripted(turns)` is a `ProviderDef` answering with scripted `Partial<AssistantMessage>`s (or functions of the request, ctx and callbacks) in order, streaming their text and recording `.requests`; register it as `extra: [{ name: "scripted", plugin: { providers: { scripted: provider } } }]`. `tempHome({ config?, secrets?, mcp?, plugins? })` points `HOME` at a temp dir and writes `~/.hortus` (config/secrets default to the `scripted` provider; a plugin is its files, or a directory path that gets symlinked) and returns the cleanup (`t.after(await tempHome())`); `HOME` is process-wide, so tests within one file must not run concurrently with it. `record()` is an `extra` plugin logging every event `{ name, payload clone }` in `.events`. `untimed(v)` drops `durationMs` (tool results' timing) from plain objects and arrays, for `deepEqual`. Stub HTTP with `createAgent({ fetch })` (`LoadOptions.fetch`), never by patching `globalThis.fetch`. `@hortus/cli/testing` exports `startCli(opts?)` (`createCli` as `hortus` sets it up: the `cli:*` pieces, `provided: { "@hortus/cli" }`, then `opts`, whose `extra` (a `scripted` provider) loads before the TUI's observer, on `opts.session` or a new one) and `renderApp(cli, { columns, rows, colors })` (the App in a fake `terminal()`, `exitOnCtrlC: false`; returns the terminal plus `app` (unmount it in `t.after`), `screen()`, `keys(k)`; `colors: true` turns Ink's chalk to truecolor until that app unmounts, so tests check drawn colors without `FORCE_COLOR`), plus `composeSlots`/`composeTools`/... to render a plugin's `cli` overrides over the built-ins, and `spawnHortus(t, args)` (runs `hortusBin` (also `@hortus/cli`'s), the built `dist/index.js`, with the current `HOME`, killed after `t`: `lines` (stdout's JSON lines), `next(pred)`, `send(obj)` (a stdin line), `exit` (the code, once stdout closed), `stdout()`/`stderr()`). A spawned hortus gets its provider from a directory plugin: `tempHome({ plugins: { scripted: scriptedPlugin("<JS source of a Turn[]>") } })` (core `testing.ts`; functions allowed, never real keys); `--plugin <file>` loads a test's own plugin module (import zod by `import.meta.resolve("zod")`; `@hortus/*` resolve through the host's hook).

## Conventions

- Source imports use `.ts`/`.tsx` extensions; `rewriteRelativeImportExtensions` rewrites them on emit. ESM only, `verbatimModuleSyntax` (use `import type`), `noUncheckedIndexedAccess`.
- Prefer `interface` over `type` for object shapes; use `type` only for unions, intersections, and other aliases an interface can't express.
- Biome: 2-space indent, 120 cols, double quotes, organized imports. Markdown is excluded (`!**/*.md`): Biome's formatter turned `---` frontmatter into headings, silently dropping skills.
- `// ponytail:` comments mark deliberate shortcuts with a known ceiling and upgrade path.

## Architecture

- **Provider-neutral messages** (`core/src/llm.ts`): `Message` is `user | assistant | tool`, each with `entryId?` (its session entry, set in session state and run histories, never sent: providers rebuild every message, and `scripted` records requests without it). A `UserMessage` has `content`, `images?` (sent before the text) and `meta?: { plugin, type, details?, display?: boolean }` (a plugin's message: plain text to the model; the CLI shows it when a plugin renders its kind, or with `display: true` in the built-in plugin-message look; `false` hides it). Each provider (`providers/*.ts`) converts to/from its own API. Assistant messages may carry `raw: { provider, content }`, replayed verbatim only to the same provider (e.g. Anthropic thinking blocks); other providers rebuild from `text`/`toolCalls` (leaving out calls the provider ran itself, which carry `result`). A `ToolResult` carries `images?: Image[]`, every one sent, `usage?` (a tool's own model calls, e.g. a subagent's; the CLI's usage line adds it to the totals) and `value?` (what `execute` returned when not text or images, its JSON being `output`: for `ctx.runTool` callers, and dropped once a `tool_result` handler changed `output`, so a redaction reaches them too; dropped from a model's calls' results, so never sent or saved). Anthropic's `raw` is keyed by endpoint and model (`anthropic <baseURL> <model>`), so a proxy's thinking blocks never reach the API or the reverse; it sanitizes foreign tool-call ids, merges consecutive user turns (tool results then a plugin's message) into one, and sends `max_tokens` from `info(model).maxOutput` (64000 when the endpoint doesn't report it; retrieved once per provider instance, i.e. per run). `Provider.info?(model)` → `{ contextWindow?, maxOutput?, efforts?, images? }` (Anthropic reads the model's `capabilities`, once per provider instance, a failed lookup kept as `{}`; `openai` reports only OpenRouter's `context_length`). `Usage.cost?` (USD) is set by providers or wrappers that know prices; the CLI's usage line totals it. OpenRouter is just an `openai`-type secrets entry with an `endpoint`. `openai` is Chat Completions; `openai-responses` is the Responses API (same `endpoint`s, OpenRouter's too): stateless (`store: false`), its `raw` is the output items without ids, keyed by endpoint and model (encrypted reasoning only decrypts for the same account, and models without reasoning reject it). Like `reasoning_effort` in `openai`, its `reasoning` and `include: ["reasoning.encrypted_content"]` are only sent for a set effort, so auto effort asks for no reasoning summaries or replayable reasoning.
- **Plugins** (`plugins.ts`): a plugin's default export is `{ providers?, tools?, on?, entries?, commands? }`; `on` handles `Events` (`llm.ts`, see the agent loop), run in plugin order with mutable payloads, each handler getting `(payload, ctx)` (except `ask`: see ctx); `entries` replays its session entries (see Sessions); `commands` are `/name arg` commands (an array, or a function of the plugin's host ctx called at every listing, for commands that come and go: `mcp-adapter`'s one per MCP prompt) (`Command { name, aliases?, description, args?, complete?(ctx) → Candidate[], enabled?(ctx) → boolean, run(arg, ctx) → text? }`), run by any host with the plugin's host ctx: `agent.commands()` lists the enabled ones (`enabled` asked at every listing; false: left out; a `commands(ctx)` or `enabled(ctx)` that throws is skipped and reported to `onError` once, so a same-named earlier one shows, and a kept `AgentCommand.run` throws) merged by name (later plugins win) as `AgentCommand`s (`plugin` stamped, `run(arg)`/`complete()` already bound), so a plugin's command is tested with the harness alone (`(await createAgent()).commands().find(...).run(arg)`), and remote hosts list and run them. Everything built in is a named **piece** (`Piece`: an in-code manifest `{ name, version, dependencies?, replaces?, order?, required?, plugin }`) in `core/src/builtin/*.ts`, importing only `../index.ts` (so `loadPlugins` imports `builtin/index.ts` dynamically, after the index has loaded): `builtin:prompt` (loads AGENTS.md into `run_start.context`, renders it with the base prompt in `prompt`), `builtin:skills` (discovery + `<available_skills>`; depends on `builtin:read`), `builtin:read`/`write`/`edit`/`bash` (one tool each; tool-specific prompt text belongs in `Tool.prompt`, none yet), `builtin:anthropic`, `builtin:openai` (`openai` + `openai-responses`), `builtin:mcp`, `builtin:codemode` (see MCP & codemode), `builtin:compaction` (see Compaction), `builtin:name` (`/name [title]`: sets the current session's name through `ctx.session`, on any host; no title shows it). Load order: built-in pieces, the host's `LoadOptions.pieces` (the CLI's `cli:*`), every `~/.hortus/plugins/<dir>/hortus.json` (`name`, `version`, `entrypoint`, `dependencies`/`optionalDependencies` as `{ name: npm-style range }`, checked with `semver`, `replaces?`, `order?: "last"`, `required?`), then `extra` (`{ name, plugin }[]`), all but `extra` sorted together by `sortManifests` (dependencies first, then `order: "last"` ones after the rest unless a dependency pulls one earlier; missing required ones or cycles throw). `LoadOptions.only` (names, or names they `replace`; a name ending in `*` matches by prefix, e.g. `builtin:*`: `isNamed`) keeps only those plugins taking part, the others keeping just their providers (`providersOnly(n)`; as a subrun's `plugins.only`; `extra` ones all stay). A manifest's `required: true` (a policy plugin: guard, safety-net, permission-system) is never left out by `LoadOptions.only` (`--only`) or a subrun's `only`/`disable`; only `disabledPlugins`/`LoadOptions.disabled` (`--disable`) remove it. `config.disabledPlugins` (plus `LoadOptions.disabled`) removes plugins by name (`prefix*` by prefix, as in subrun filters): a required dependency on one throws naming both, an optional one is skipped. `replaces: [names]` drops those plugins and satisfies dependencies on them, unchecked; a replaced replacer passes its `replaces` on to its own replacer (chains end at a loaded plugin; cycles throw); two loaded replacers of one name throw (suggesting `disabledPlugins`). Tools and providers merge in load order (`mergePlugins(named[], onError?)`, exported so a filtered plugin list can be merged anew): a plain def named like an earlier one is a conflict, reported to `LoadOptions.onError(plugin, error)` (default: throw; the CLI shows an error line) and skipped; a `ToolWrap` `{ name, wrap(Default) }` / `ProviderWrap` `{ wrap(Default, ctx) }` (`ctx`: the wrapping plugin's host ctx, so it reaches the `ctx.state` its handlers use; `mergePlugins(named, onError?, ctxOf?)` passes it, and `createAgent` loads with `loadNamed` and merges once the host ctx exists) layers over the earlier def (a wrap of nothing is reported too, unless it has `optional: true`: then it is skipped silently); `providers["*"]` wraps every type, later plugins' too, outermost (`mergePlugins` also returns `innerProviders`, the defs without `"*"` wraps). `provided` names (the CLI's `{ "@hortus/cli": version }`) satisfy dependencies, version-checked, without loading anything (a plugin with such a name is a duplicate). `loadPlugins` also returns `plugins` (`Named`: `{ name, plugin, replaces?, required?, builtin? }`, `replaces` being every name it stands in for, chains included, and `required` too when one of those is; `builtin`: a piece) in load order, for host keys like the CLI's `cli`. Both packages export their `version`, which their pieces carry. Define tools with the `tool()` helper (zod `inputSchema`, which validates the input and is declared via `z.toJSONSchema`, unless `jsonSchema` is set: that is declared as is, e.g. an MCP server's, with `z.looseObject({})` leaving validation to the tool; `toolSchema(t)` is the declared one, which providers and codemode use); `execute(input, ctx: ToolCtx)` returns text, images, any other value (its JSON the output, the value `ToolResult.value`) or `toolResult({ output, value?, images?, isError? })` (text for the model and a value for `ctx.runTool` callers at once; `Tool.outputSchema`, a JSON Schema of `value`, is codemode's declared return type), and may call `ctx.update(details)` to report progress (a `tool_update` event, not saved), and the last value, as its `tool_update` handlers left it, becomes the result's `details` (`undefined` = none): saved with it and shown by renderers, never sent to the model (providers copy only `output`/`images`). `mergePlugins` stamps each tool with `plugin`: the one that provided it (a wrap keeps it, so the wrapped original gets its own plugin's ctx; a wrapper keeps its state by closure).
- **Agent loop** (`agent.ts`, types in `llm.ts`): `createAgent(opts?: LoadOptions)` loads config and plugins once (a plugin in `opts.extra` runs last; it's how callers observe a run, as `cli.ts` does), then fires `init` (host ctx; plugins keep it for timers and sockets), then `ready` (after every `init` handler finished). The agent owns the **current session**: `agent.setSession(s, reason?: "new" | "resume")` fires `session_close { session, reason, target, cancel? }` for the one before (`target`: `s`, the session being switched to; `cancel = true` keeps it: resolves false) then, unless cancelled, `session_closed { session, reason, target }` (end per-session work there: no later handler can keep it) and `session_open { session, reason }` ("start" for the first); `agent.session()` returns it. `agent.close({ timeout = 3000 })` (exit) aborts every run (`aborted = { by: "host", reason: "exit" }`), waits for them, then fires `session_close("exit")` (cancel ignored), `session_closed("exit")`, `session_closed("child")` for every child not done yet, and `close` (where plugins flush per-run state of runs cut off before their `run_end`), each wait cut off by the timeout, (builtin:mcp stops its servers in `close`); from the start runs and `send` throw, except that those handlers may still `ctx.subrun` (and run or send on the sessions of children they made: a child from before `close` starts nothing more, its queued sends resolving with undefined; an aborted run's `ctx.subrun` throws) until they have finished (or timed out), when what is left is aborted and `subrun` throws too. `run(input?: string | UserInput, { model?, provider?, effort?, signal?, session?, source? })` runs on `session` (default the current one, else a fresh in-memory `memorySession()`; one run per session at a time: a run on a session that has one waits for it to end, and its lane counts it until its leftover sends are queued), its history being exactly the session's messages (no copy of its own): with `input`, `input { text, images?, meta?, source (default "user"), handled }` fires first, with `ctx.run` already set (resolved first; left unset if the provider or model doesn't resolve, which the run then reports) (`handled` → no run, resolves undefined; edits change the saved message), then the user message is added; `run_start.messages`, each request (a `response.retry` too) and `RunEnd.messages` are the session's messages as they are then (so what was persisted mid-run, like a reducer rewriting `messages` for compaction, applies from the next request); model/provider default to the session's (then config's), effort to the session's unless `effort` is a key of the options (the CLI passes `runEffort`, `undefined` meaning the provider's default). Every message the run adds (user, sent, assistant, tool) is appended to the session as it completes and fires `message`. When the run ends, the next `send` queued on that session starts, else `idle { session }` fires (with a host ctx on that session, once the run has settled, so `run` resolves first and an idle handler may await a run it starts; never for previews, nor once closed; after `close` queued sends start nothing and resolve undefined). It resolves provider/model/entry per run (`ProviderDef.create(entry, { name, headers?, fetch?, auth?, providers? })`: the whole secrets entry, `${VAR}`-expanded; the agent passes `fetch` (`LoadOptions.fetch`, default the global one), `auth` (`ctx.secrets.get(name, opts)`) and `providers` (`innerProviders`, so a routing provider like the `litellm` reference plugin delegates to the registered `anthropic`/`openai` defs, their named wraps applied and `"*"` ones not twice); wrappers pass `headers`/`fetch`, which the built-in factories hand to the SDKs) and resolves with `RunEnd` `{ source, messages, error?, aborted? }` (also when aborted; it rejects when the run failed). One run: `input → message (user) → skills → run_start → prompt → (turn_start { index } (from 0; not for previews) → request → text/thinking/tool_input* → response → [provider-run tool_call → tool_result]… → message → [tool_call → tool_gate (per call)… → tool_update* → tool_result…] → message → turn_end → message (sent/steered, at the turn boundary)*)* → run_end` (in a `finally`, once). `run_start { source: "run" | "preview", tools, skills?, context, messages (frozen), model, provider, effort? }` sets the callable set (a duplicate name is reported, the later dropped), may change model/provider/effort (re-resolved) and edits `context` (`ContextFile[]`, the AGENTS.md files builtin:prompt pushed); `prompt { system: [], tools, skills, context }` collects the system prompt parts (pieces write theirs there, so a removed tool leaves no text). Every provider call, `ctx.complete` too, takes one path: `effort` fitted to `info(model).efforts` (`fitEffort(effort, efforts)`: as is when taken, "off" → the lowest level, a level → the nearest below, else above), `maxTokens` filled (unless set) from `info(model).maxOutput` (asked once per `<provider>/<model>` for the agent's life, a failure kept as none: the OpenAI providers' `info` pages the whole model list; Anthropic sends it as `max_tokens`, else its own model lookup's, else 64000; the OpenAI providers send no limit), `request` (`RequestEvent`: the `CompletionRequest` fields plus `id`, `source` = "run" / "preview" / the calling plugin, and observe-only `provider` (entry name) / `type`, stripped before the call; edits apply to that call only; `messages` is a deep copy without tool results' `details` and `durationMs`, `tools` a shallow one; tools with `exposure: "codemode"` aren't declared unless a handler adds them; after the handlers, results in a `tool` message answering no call of the message before it (a history rewrite cut the call away) are left out, and every model-run call no `tool` message right after its assistant message answers (a crash or kill mid-tool, wherever user messages landed after it) gets an `{ output: "Interrupted", isError: true }` result there (merged into that message or a new one; the session file is left as is), as providers reject unanswered calls, and the declared tools' `Tool.prompt`s are appended to `system` as one `\n\n`-joined block unless it already ends with exactly that block (so a sent request's or preview's `system` can be reused with its tools), so tool guidance comes and goes with the declaration, and a codemode-only tool's is never sent), `provider.complete(req, callbacks, ctx)`, then `response { id, request (frozen: what was sent), payload?, assistant?, error?, meta?: { stopReason, responseId, model, status, headers }, retry? }` (handlers may change `assistant`; `retry` re-sends once; an SDK error's `status`/`headers` fill `meta`). A model's call resolves against that request's declared tools (else "Unknown tool"); only `exposure: "direct"` (default) tools are declared, others are callable through `ctx.runTool` only. Each request declares from the run's tools as they are then (`ctx.tools`), so one a tool or handler pushes there mid-run is declared from the next request on (and one removed, undeclared). Each call passes `tool_call { call (a copy: `input` edits apply to execution only, validated after every handler), result?, env? }` (mutators: `env` becomes `ToolCtx.env`), the first `result` set is final and skips execution, a throwing handler blocks the call (`Blocked by <plugin>: …`); then, for gates, `tool_gate { call, tool?, env?, result?, block? }` on the call as it will run, deep-copied and frozen (the tool gets a copy of exactly that input; `tool` the tool it resolves to, by the frozen call's name (a `tool_call` handler may rename it), `result` one a `tool_call` handler supplied): `block = "<output>"` or a throw blocks, the first block final, replacing even a supplied non-error result (fail closed); not fired for provider-run calls (a `ToolWrap` adding env inside `execute` is part of the tool, ungated). All calls of a batch pass both, handler by handler, before any runs. Then they run (in parallel; `sequential` tools alone, after; once the run is aborted, a call not yet started gets an `Aborted` error result instead; a run tool's result gets `durationMs`, how long `execute` took, saved, never sent; none for a handler-supplied one) and `tool_result { call, result }` follows each (a handler may replace `result`; the payload's is used, with the call's `id`; one that isn't an object is ignored; images it added without a `path` are then saved like returned ones). `tool_update { call, details }` reports a running call's `ctx.update`. A call the provider ran itself (`ToolCall.result` set) passes `tool_call` and is reported before its assistant `message` (which carries the result its handlers left), not run or answered, and alone doesn't continue the loop. `turn_end { assistant, results?, stop }`: `stop` ends the run (it starts true when a tool called `ToolCtx.stop()`); after it (the turn boundary) messages sent during the turn join the history and a `steer` among them sets `stop = false`, unless the run was stopped (aborted, or `stop` set by a handler while tools ran), when they act as if sent when idle, after `run_end`. Other throwing handlers are reported to `LoadOptions.onError(plugin, error)` (default: print to stderr; load conflicts keep their default throw) and the next handler runs; only an `onError` that throws fails the run. Deltas and `tool_update`s are queued in order and handled before the `response`/`tool_result` after them; their handlers' ctx has its own queue, so they may await `ctx.complete`/`ctx.runTool`. Tool errors and invalid input are returned to the model as `isError` results, not thrown.
- **ctx** (`Ctx` in `llm.ts`): handlers get `(payload, ctx)`, tools `ToolCtx` (`ctx` + `callId`, `parentId?` (the calling tool's call id, for a `ctx.runTool` call), `update`, `stop()` (ends the run after this batch, Pi's `terminate`), `env?`: extra environment variables for processes the tool starts (the `tool_call` handlers' `env`), which builtin:bash merges into its child's; a wrapper passes `{ ...ctx, env }` to `Default.execute`), providers `complete(req, callbacks?, ctx?)`. Fields: `plugin` (the name the ctx's plugin was loaded under, "host" for the host ctx; its entry types are `${ctx.plugin}:<type>` and its `state.data` key, so a renamed install reads and writes consistently under its new name; entries saved under the old one no longer replay), `run?` (`RunInfo` `{ id, depth (0; a subrun's is its caller's + 1; under `LoadOptions.parent` top-level runs are that session's children), parent? (a subrun's: `{ session?, runId?, toolCallId? }`, the caller's session, run (none from a command) and tool call (only from a tool); under `LoadOptions.parent`: `{ session }`), agent? (`SubrunOptions.agent`), root? (the top-level session's id: a top-level run's own, a child's its caller's, under `LoadOptions.parent` its tree's root), provider, type, endpoint?, model, effort?, info (the provider's `ModelInfo`for the model, from the same cache as`maxTokens`; `{}`when unknown), source (who started it:`input.source`/`RunOptions.source`, default "user"), cwd }`), `cwd` (the run's, else the session's `cwd`, else the process's: built-in pieces use it, never `process.cwd()`; `read`/`write`/`edit` resolve paths against it, `bash` runs in it, `builtin:prompt`/`builtin:skills` look for AGENTS.md and skills from it), `subrun(input, opts?)` (see Subruns), `session?` (the run's; the host ctx's is the current one at the time of use, so a ctx kept from `init` follows `/new`, except in `idle` and in the `message` of a send appended outside a run: that session; a preview may have none), `send(msg, { deliver?, model?, provider?, effort?, source? })` (a user message to the ctx's session, resolving with the `run_end` of a run it starts or steers, else undefined: `"context"` (default) joins the running run at its next turn boundary without forcing a model call, or is appended at once when idle; `"steer"` likewise but keeps the run going, and starts a run when idle (one sent from outside between a run ending and a queued one starting, e.g. while the host holds its `onWake`, becomes a run of its own after that one instead of steering it); `"after"` starts a run once the current one ends; from a run's own `input`/`run_start`/`prompt` handlers every mode joins before its first request (another sender's sends to a run still starting wait for its first turn boundary, "after" for its end), from `run_end` every mode acts as when idle; a preview's never starts a run (before its request it joins the preview only, later it is "context"); `model`/`provider`/`effort` apply to the run it starts, whose `input.source` is `source` (default the sending plugin); runs are started through `LoadOptions.onWake(start, session)` (the host calls `start(hostOpts)` when ready; default at once); from a run's own ctx (its handlers and tools) `"steer"`/`"after"` resolve at once with undefined, as the run they reach can't end while the sender awaits it), `callId?` (the acting tool call; events a tool's `complete`/`emit`/`runTool` cause carry it), `signal` (the run's: Esc and `abort` reach tools, `bash` kills its process group; there is no `ctx.exec`: plugins use `node:child_process` with it), `abort(reason?)` (`run_end.aborted = { by: <plugin> | "user", reason? }`; from a ctx outside a run (the host ctx, `idle`'s), the runs on its session, every run when it has none; `agent.close` aborts every run), `busy()` (a run is going on the ctx's session; with none, on any), `tools` (the run's callable set; outside a run, the agent's: every loaded tool plus those plugins pushed there since, e.g. builtin:mcp's once connected, and each run's `run_start.tools` starts from a copy of it; pushed tools aren't `Plugin.tools` entries, so a `ToolWrap` can't wrap them: replace one in place in the host array instead; a tool pushed through a plugin's `ctx.tools` without `plugin` gets that plugin's, in place, so its `ctx.state` is the plugin's), `plugins()` (the plugins taking part where the ctx is: `{ name, builtin, required, replaces? }`), `pending()` (the sends waiting on the ctx's session, `{ deliver, source, message }`: the run's inbox, then those queued after it), `runTool(call, { signal? })` (gated like a model's call; from a tool, id `<callId>/<n>` with `parentId`; the CLI shows only top-level blocks; `signal` aborts that call alone: its `ToolCtx.signal` (and its `complete`/`ask`/nested calls') is it combined with the caller's, so a script's timeout cancels the calls it left running), `state` (typed: `stateOf<S>(ctx, key, init)` is `ctx.state[key]`, made by `init()` the first time; the plugin's own object for this agent: the same one for its handlers, tools (by their `plugin`; a tool without one gets a state of its own per name, never a plugin's) and commands, in and out of runs; per-agent connections and caches go there, not in module state, as builtin:mcp's and `mcp-extension`'s do), `complete({ messages, system?, tools?, provider?, model?, effort?, maxTokens?, temperature? (sent by the built-in providers only when set; Anthropic takes it only with effort "off"), headers?, signal? })` (the run's provider and model, else config's, unless named; not streamed to the host; `signal` aborts that call, e.g. `AbortSignal.timeout(ms)`, as the run's does), `listModels()`, `resolve(opts?)` (the provider (secrets.json name), `type`, `endpoint`, model and `info` a run on the ctx's session would use, `{ provider?, model? }` (`agent.commands()`, aliases too, e.g. `name` renames the session; reply `{ response: "command", id?, name, text? }`), `set_session { session: <id> | "new" | "memory" | "key:<key>" }` (`agent.setSession`, reason "new" for a session nothing was written to yet; reply `{ response: "set_session", id?, session, ok }`), `exit`; a failed command's one reply is `{ response: <type>, id?, error: { name, message } }`; a positional prompt is run as a `prompt`; stdout gets every event, plus an ask as `{ event: "ask", payload: { askId, ...request } }` (its `show()` called as it's written) and `{ event: "answered", payload: { askId, by?, reason, answer? It is one more `ask` handler (pending until answered or the ask's signal aborts), runs plugins' sends through its `onWake` (abortable), fires `interactive` once the agent is up; when stdin closes it turns non-interactive, lets its asks settle unanswered, waits for its runs, and exits 0 (`ctx.exit()` too). A plugin spawning hortus uses `hortusBin` (`@hortus/cli`: its `dist/index.js`, the running host's own through the resolve hook): `spawn(process.execPath, [hortusBin, ...])`. Under `-p`, whatever a plugin delivers after the last run and queued send have ended (a background job's late notification) is lost when the process exits.
